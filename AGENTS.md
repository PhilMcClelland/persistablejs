# Persistable.js, for agents

You are adding shared data to someone's web prototype. Persistable.js gives every visitor the same JSON objects through one script tag.

0. **Does it need a backend yet?** If the person is only starting, or the data need not be shared, there is nothing to deploy: copy `stores/session.js` beside `persistable.js`, load it after it, and use `Persistable({ store: 'session' })`. The data stays in the browser tab. Moving to a shared store later changes that one line.
1. **Is there a store yet?** Ask the person for their store address (`https://persistable.<subdomain>.workers.dev`). If they have none, follow `SETUP.md` once; it deploys `worker.js` to their own free Cloudflare account and proves it with a verify script. Do not skip the verify.
2. **Add the client.** The files come from this repo, `https://github.com/PhilMcClelland/persistablejs`; if you do not have it, clone it. Copy `persistable.js` next to the prototype's pages, unchanged, and load it with a script tag. Then `const db = Persistable({ url: '<store address>' })`.

   In a prototype built with a bundler or a framework (Vite, Next.js and the like), do not import it. Put `persistable.js` in the folder the tool serves as it is (`public/` or `static/`), load it with a script tag in the page's HTML, and use the global `window.Persistable`. Create the client in the browser only (in an effect, or after a `typeof window !== 'undefined'` check), never while the page is being rendered on a server: it needs the page's address and the browser's storage.
3. **Pick the space.** By default the data goes in a space named after the page's origin (scheme, host and port). That is one space per prototype only when each prototype has an origin to itself. Projects under one GitHub Pages address (`someone.github.io/one`, `someone.github.io/two`) share an origin, and so does every project run on the same `http://localhost` port. Then pass `space: '<a name for this prototype>'`, or they will read each other's collections.
4. **Model the data.** One collection per kind of thing (`db.collection('votes')`). A collection name is up to 40 lower-case letters, digits, `-` and `_`, starting with a letter or digit: `votes` or `design-notes`, not `Votes` or `designNotes`. Put what belongs to its author in `data` and what anyone may change in `open`. Hang replies and other children off a `parent`.
5. **Keep it live.** Call `list()` once to draw what is already there, then `db.collection('votes').subscribe({ onCreate, onUpdate, onDelete, onResync })` hands the page each change from then on. `subscribe` says nothing about what was stored before it was called. On `onResync` read the collection again with `list()`.
6. **Decide who gets in.** Ask the person two things: who should see the data (anyone, the people they send the link to, or separate groups who must not see each other's), and whether the prototype's site already knows who a visitor is (a sign-in, a password for each client). Separate groups, or real names, on a site that knows its visitors: use a token, `docs/access.md`, "A token from your own site". It is the one way in that needs code on the site's server, so say so, and on a static host offer `key: 'link'` with a copy of the page for each group. Never keep groups apart with a `space` the page chooses: a visitor can choose another. Otherwise: If the page is public and the data should stay among the people they send the link to, use `key: 'link'`. If the page is public and everyone should see the data but only invited people should change it, run `node readkey.mjs --new`. It prints two things: a read key, which goes in the page (`key: 'link', read: '<read key>'`), and a key, which lets its holder write. The key belongs only in the link: give the person the page's address with `#k=<key>` on the end to send to those people, and put it nowhere else, not in the page, a commit, a log or a message to anyone but the person. If the page is already behind a sign-in or password, a fixed `key` in the page does the same job. With neither, anyone who finds the store can read and add. `docs/access.md` has the detail.

Rules:
- Never put a secret in a public page. A fixed `key` belongs only in a page that is itself behind a sign-in or password.
- Treat everything the store returns as written by a stranger, because without a key it may have been. Put stored values into the page as text (`textContent`), never as HTML, and never into a link, a style or a script without checking them.
- A fresh deploy answers any website. Before the address is in a page other people can see, do `SETUP.md`, "Before the address is public" (`ALLOW_ORIGINS`), and tell the person what it does not stop. Once it is set it also turns away the prototype on `http://localhost` and pages opened from a file, until their origins are listed.
- Do not store anything private. Anyone with the prototype's link can read the data, and can pass the link on.
- If the person's data should be in Supabase and not on Cloudflare: `stores/SUPABASE.md`. The page then loads `stores/supabase.js` after `persistable.js` and passes `store: 'supabase'`; everything else in this file is the same, except that link keys and read keys are the Worker's only (`docs/stores.md`).
- To read or change the data yourself, from a script: `docs/http.md`. Make one random secret, keep it in an env file between calls so you stay one person, and never type it into a command.
- Do not edit a copied `persistable.js`. Changes belong in this repo.
- The full client API is in the comment at the top of `persistable.js`; the store's addresses are in the comment at the top of `worker.js`, and its limits are the constants just below it.

Working on this repo itself: there is no build. After any change run `PERSISTABLE_VERIFY_MOCK=1 node verify.mjs https://mock.invalid` and `PERSISTABLE_VERIFY_MOCK=1 node verify.mjs --store supabase https://mock.supabase.co mock-key`, and the six test files in `tests/` (`node tests/limits.mjs`, `node tests/rules.mjs`, `node tests/readkey.mjs`, `node tests/token.mjs`, `node tests/client.mjs`, `node tests/stores.mjs`; `tests/mock-supabase.mjs` stands in for a Supabase project, and `tests/mock.mjs` is what they run on, not a test). Every change in behaviour gets a check there, or in `verify.mjs` when it is about a deployed store. Before a deploy run `npx wrangler@4 dev` and `node verify.mjs http://127.0.0.1:8787`.
